# 複数写真の一括アップロード＋自動グループ化（フェーズ2）— 設計

作成日: 2026-08-16 / 対象: デート記録アプリ / 種別: 新機能（写真の入口を"まとめて"に）

## 位置づけ（大きな機能の第2フェーズ）
「複数写真を一括アップロード → 自動グループ化 → 確認UI → 保存」の**本体**。フェーズ1（写真のCloud Storage移行, [[maprecord-photo-upload-plan]]）が土台。
- フェーズ1（完了・稼働中）：写真を Cloud Storage へ（枚数上限が消えた）。
- **フェーズ2（本spec）**：一括選択 → EXIFで日時/GPS抽出 → 日付＋近接で自動グループ化 → 確認・修正UI → まとめて保存。
- フェーズ3（別spec）：各グループの店名を Gemini＋Places で候補提案・絞り込み（backend必須）。

本フェーズは**あくまで通過点**。出力（グループ＝代表写真＋座標＋placeId を持つ記録）が、後からGeminiに渡しやすい形になるよう設計する。

## 背景・ゴール
現状は写真を1枚ずつ、1記録ずつ手動で追加する。デートで数十枚撮ったあと「1件ずつ」は重い。
→ **数十枚をまとめて選び、自動で"訪問ごと"に束ね、人が軽く直して一括保存**できるようにする。手間を「枚数分」から「訪問数分」に減らすのがゴール。

## スコープ
**含む：** 一括選択、EXIF（撮影日時・GPS）抽出、自動グループ化（下書き）、確認・修正UI（結合/分割/場所/日付/ジャンル）、一括保存。
**含まない（明確に）：**
- **店名の自動提案（Places近隣検索）／Gemini** → フェーズ3。v2の店名は**既存の手動「Googleの場所と紐付け」検索を流用**（本人選択）。
- **新しいAPI課金を増やさない**（Placesは既存の手動検索が叩く分だけ）。[[maprecord-billing]]
- 個別写真を任意グループへドラッグ移動する専用UI（分割＋結合で代用＝YAGNI）。

## 絶対要件・前提
1. **写真アップロードはフェーズ1を再利用**：`App.photos.toStoredMany(files, groupId, onProgress)` でStorageへ。孤児防止のロールバックもそのまま効く。
2. **プライバシー**：EXIF読み取りは**端末内のみ**（送信しない）。Storageルール等はフェーズ1のまま。
3. **記録は地図のピン＝座標必須**：位置の無いグループは保存しない（下記）。
4. **既存の単発追加フローは残す**（一括は"別の入口"として追加、置換しない）。

## 全体フロー
① 「写真からまとめて追加」→ 一括選択 → ② 各写真のEXIF抽出（日時・GPS）→ ③ 自動グループ化（下書き）→ ④ 確認・修正UI → ⑤ 位置のあるグループを1件=1記録で保存。

## ③ グループ化アルゴリズム（下書き生成・純粋関数）

**入力：** 写真ごとに `{ file, time, gps: {lat,lng} | null }`。
- `time`：EXIF `DateTimeOriginal`（無ければ `CreateDate`/`ModifyDate`、それも無ければ `file.lastModified`）。
- `gps`：EXIFのGPS（`exifr` で抽出）。無ければ `null`。

**束ね方（時系列に走査して"切る"）：**
- **GPSあり写真**：時刻順に、次のどちらかで新グループに切る——
  - グループ中心（既メンバーの座標平均）から **150m** より離れる、または
  - 直前の写真から **2時間** 以上あく。
- **日付では切らない**（日またぎの深夜デートが割れないように）。
- **GPSなし写真**：座標が無いので**時間の空き（2時間）だけ**で束ね、「**場所未設定**」グループにする。
- **各グループの日付＝そのグループの最早写真の日**（日をまたいでも前日に寄る）。

**各グループが持つもの：** 写真配列（時刻順）／代表写真＝先頭（最早）／中心座標（GPSありのみ）／日付／GPS有無フラグ。

**性質：** 完璧でなくてよい"下書き"。ズレは④で人が直す。閾値(150m/2h)は定数（後で調整可）。

## ④ 確認・修正UI

グループを**撮影時刻順に一列**でカード表示（**場所未設定も時系列で"間に"入る**）。1カード＝1グループ＝保存で1記録。

**各カードの表示：** 代表写真＋枚数、日付・時間帯、写真ストリップ（時刻順）、場所（紐付けボタン）、ジャンル、日付。
**操作：**
- **結合**：カードの「↑前のグループと結合」で1つ上（時系列で前）のグループに統合。場所を引き継げる。
- **分割**：ストリップの写真をタップ →「✂️ここで分割」で、その写真から後ろを新グループに切り出す。
- **場所（手動）**：既存の「Googleの場所と紐付け」検索を各グループで使う。**紐付けた店の座標を、そのグループの記録座標に採用**（特にGPSなしグループはこれで座標を得る）。placeIdも保存。
- **日付・ジャンル**：カード上で編集。
- **代表写真＝ストリップ先頭**（＝ピンの写真）。後から通常の編集画面で変更可（既存機能）。
- **カード削除**：そのグループを保存対象から外す。

## ⑤ 保存モデル

「すべて保存」で、**位置のあるグループごとに**記録を作成：
- `date`＝グループ日付／`lat,lng`＝GPS中心 または 紐付けた店の座標／`placeId`（紐付け時）／`genre`／`photos`＝`toStoredMany` でStorageへ（先頭＝ピン写真）／`memo`＝空（後で編集で追記）／`order`＝その日の末尾。
- **位置なしグループはスキップ**して画面に残し、「場所を設定して」を強調表示（保存はブロックせず、他は保存する）。
- **進捗表示**：全体で「アップロード中 n/N枚」。**失敗したグループ**はフェーズ1のロールバックで孤児を残さず、カードを画面に残して再試行可能にする。

## データ形状

```
// ④のメモリ上の下書きグループ（保存前）
Group = {
  photos: [{ file, time, gps }],   // 時刻順
  date,                            // 'YYYY-MM-DD'（最早写真基準）
  center: {lat,lng} | null,        // GPSありのみ
  hasGps: boolean,
  placeId: string | null,          // 手動紐付け
  place: {lat,lng} | null,         // 紐付けた店の座標
  genre,
}
// ⑤で作る記録（既存スキーマそのまま。フェーズ1の写真形）
Record = { date, name, genre, memo:'', tags:[], order, lat, lng, photos:[{url,thumbUrl,path,thumbPath}], placeId? }
```

## Phase 3（Gemini）への布石
各記録が「代表写真＋座標＋placeId」を持つので、後から「代表写真＋その座標の Places 近隣候補」を Gemini に渡して店名を絞る、が自然に乗る。v2では追加の保存項目は不要。

## 検証方針
- **純粋関数（グループ化・fitSize同様）は `_selfTest`**：時刻/座標の配列 → 期待するグループ分割、を devtools コンソールで検証（150m/2h境界、日またぎ、GPSなし、代表写真=先頭）。ここが自動テストの中心。
- **実機確認（本人スマホ）**：数十枚を一括 → 妥当な下書き → 結合/分割/場所付け → 一括保存 → 各記録が正しくできる。位置なしグループのブロック挙動。HEIC混在。大量アップの進捗・失敗リトライ。

## リスク・注意点
- **EXIFライブラリ依存**：`exifr`（`exif-check.html` で実証済み）。CDN読み込み失敗時のフォールバック（日時=lastModified、GPS=null で続行）。
- **大量アップの負荷**：数十枚×2サイズは重い。フェーズ1の進捗＋ロールバックを活用。モバイルの発熱/中断に注意。
- **グループ化の"塩梅"**：閾値は初期値。ズレ前提で結合/分割UIを最優先で作り込む。
- **iOS/HEIC**：フェーズ1同様、canvas経由でJPEG化。実機確認。
- **座標が地図アプリの必須項目**：位置なしグループの保存ブロックを忘れない。

## 次フェーズに持ち越す決定（記録）
- **店名の自動候補**：Places近隣＋Gemini絞り込みはフェーズ3。placeIdはPlacesから取得（Geminiは選ぶだけ）。backend(Cloud Functions)必須。
- **同一スポット判定の高度化**：現状は座標近接(150m)。将来 placeId 一致を優先し得る（[[maprecord-search-feature]]）。
