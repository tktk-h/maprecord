# Geminiで店名を自動提案（フェーズ3）— 設計

作成日: 2026-08-18 / 対象: デート記録アプリ / 種別: 新機能（AIによる店名提案・初のバックエンド）

## 位置づけ（大きな機能の第3フェーズ・最終）
「複数写真を一括アップロード→自動グループ化→確認UI→保存」の仕上げ。フェーズ2（[[maprecord-photo-upload-plan]]）で作った一括確認UIに、**AIによる店名の下書き**を足す。
- フェーズ1（完了）：写真を Cloud Storage へ。
- フェーズ2（完了・本番稼働）：一括アップロード＋自動グループ化＋確認UI＋保存。位置は GPS/店名検索/地図ピンの3通り＋名前手入力。
- **フェーズ3（本spec）**：確認画面で、各グループの代表写真＋近くの店候補を Gemini に渡し、**店名を自動で下書き**する。初めて**バックエンド（Cloud Functions）**を持つ。

## 背景・ゴール
フェーズ2で「一括→グループ→保存」までは軽くなったが、各グループの**店名付けは手動**（検索 or ピン）。デートで数グループあると、それぞれ検索するのがまだ手間。
→ **確認画面を開いた瞬間に、AIが写真を見て店名を先埋め**する。人は確認して直すだけ。手間を「グループごとに検索」から「AIの下書きを確認」へ。

## 決定事項（ブレストで確定）
- **トリガー**：確認画面を開いたら、**位置のある全グループを自動でAI提案**（名前を先埋め）。
- **編集で増えたカードは自動対象外**（分割で新規作成など）→ **手動「✨AIで提案」ボタン**で1回だけ。
- **候補も表示**：近くの店候補をチップで並べ、Geminiの推しに✨。タップで別候補に切替可。
- **Geminiは無料ティア**（本人選択）。写真がGoogleの学習・人間レビューに使われ得る建付けを承知の上（[[maprecord-billing]]）。デート写真は「普通のスナップ、悪用の心配はしない」と判断。
- **自信がなければ"該当なし"→名前は空のまま**（間違った店名を入れない）。

## スコープ
**含む**：Cloud Function 1つ（Gemini呼び出し）、確認画面での自動/手動提案、候補チップUI、失敗時の手動フォールバック。
**含まない（YAGNI）**：Places呼び出しの関数化（クライアントの `nearbyPlaces` のまま）、有料ティア対応、位置なしグループの自動提案、履歴/学習の作り込み。

## 構成・データフロー
```
確認画面を開く（フェーズ2の bulk.js レビュー）
  └ 位置のある各グループについて（少しずつ順に）：
      1. フロント: App.places.nearbyPlaces(中心座標) で近くの候補を取得（既存・Places・クライアント側）
      2. フロント: Cloud Function suggestPlace に { 写真(サムネ), 候補[] } を送る
      3. Function: Gemini(Flash) に「この写真はどの候補？自信なければ該当なし」と聞く
      4. Function: { placeId: 選択 or null } を返す
      5. フロント: placeId が返れば名前/placeId/座標/ジャンルを先埋め＋候補チップ表示（✨=推し）
```
- **位置なしグループは自動対象外**（座標が無い→ `nearbyPlaces` が呼べない）。位置を手動で付けた後に手動ボタン。
- **送る写真はサムネ(~400px)**（軽い・速い・露出最小）。

## UI（確認カードへの追加）
- **名前欄**：AIの選択を先埋め（`✨AIが提案` バッジ）。自信なしは空欄。
- **候補チップ**：近くの候補を数個（〜6件）タップ可能で並べ、Geminiの推しに ✨。別チップをタップでそこに切替（placeId/座標/ジャンルも差し替え）。
- **AI判定中**：開いた直後、判定完了までカードに「AI判定中…」。
- **手動ボタン**：編集で増えたカード／位置を後付けしたカードに「✨AIで店名を提案」（押した時だけ1回）。自動済みカードには「もう一度提案」。
- **既存手段（🔍検索・🗺地図でピン・名前手入力）はそのまま**残す。
- AIはあくまで下書き。最後は人が確認して保存。

## バックエンド（Cloud Function `suggestPlace`）
- **形態**：Firebase の**呼び出し可能関数（callable）**＝ログイン済みユーザーのみ呼べる。
- **保持するもの**：Geminiの**APIキーだけ**（関数の秘密設定 / 環境に置く。無料ティアの鍵）。
- **入力**：`{ imageBase64: string(サムネJPEG), candidates: [{ placeId, name, genre }] }`。
- **処理**：Gemini Flash（例 `gemini-2.0-flash`）に画像＋候補リスト＋指示（看板/料理/内装/ロゴ等で判断、該当なしは null）。低temperature、JSON回答（選んだ index か placeId、なければ null）。
- **出力**：`{ placeId: string | null }`。
- **関数はGeminiだけ叩く**（Placesはクライアントの既存呼び出しのまま＝関数を薄く保つ）。

## 自信度・エラー・レート制限
- **unsure**：Gemini が迷えば null → 名前は空のまま。
- **レート制限**：無料ティアは1分あたり十数回・1日上限あり。開いた時に全グループを**数件ずつ順に**呼んでバースト回避。
- **失敗時**：個別カードは静かに「提案なし」に落ち、**手動「✨AIで提案」でリトライ可**。**保存は絶対ブロックしない**。
- **タイムアウト**：1呼び出しに妥当な上限（例 15秒）。超えたら提案なし＋手動。

## プライバシー
- 端末から外に出るのは **サムネ画像＋候補の店名テキストだけ**（他の個人情報は送らない）。
- **無料ティア＝Googleの学習・人間レビューに使われ得る**建付けを承知の上（本人了承）。将来固くしたければ有料ティアへ切替可（関数側の設定変更のみ）。

## 前提・依存
- **フェーズ2の `bulk.js`（確認UI）** に追記する形。グループは `{ photos:[{file,...}], center, hasGps, placeId, place, manualLoc, name, genre }`。
- **送るサムネの作り方**：確認画面では写真はまだ `File`（未アップロード）。代表写真（`photos[0].file`）を**フェーズ1の `App.photos.compressToBlob(file, 400)` で小さいJPEGにして base64 化**して関数へ送る（既存の圧縮関数を流用）。
- **`App.places.nearbyPlaces(lat,lng,{radius,max})`**（既存）で候補取得。
- **Firebase Functions の初期セットアップが新規**（`functions/` ディレクトリ、Node、デプロイ）。Storageルール同様 Firebase CLI 管理（[[maprecord-deploy]]）。

## 検証方針
- **純粋部分は限定的**（本体はGemini＋認証が要る）。フロントの「候補整形→関数呼び出し→反映」の配線は実機確認が中心。
- **実機確認（本人）**：一括→確認画面で自動提案が出る／✨推しと候補チップの切替／自信なしは空欄／編集で増えたカードは手動ボタンのみ／失敗しても保存できる／体感速度。
- **プライバシー確認**：関数はログイン必須で呼べる（未ログインで叩けない）こと。

## リスク・注意点
- **Geminiの正答率は写真次第**（看板/ロゴが写れば高い、料理だけだと外しやすい）。だから「下書き＋人が確認＋候補チップ＋該当なし」で外れても痛くない設計にしている。
- **初バックエンド＝保守が増える**（デプロイ、鍵管理、Node依存）。最小構成を保つ。
- **無料ティアの上限/規約変更**：レート/日次上限に当たったら手動フォールバック。学習利用の規約は承知。
- **キー漏洩防止**：APIキーは関数の秘密に置き、フロントやリポジトリに絶対置かない。
