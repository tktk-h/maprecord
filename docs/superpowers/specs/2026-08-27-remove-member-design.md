# 相手をスペースから外す Design

**日付:** 2026-08-27 / **版:** 20260827q

## 何をする機能か

設定から相手をスペースの members から外し、記録も写真も見られなくする。
「相手をログアウトさせる」に一番近いことがこれ。
**他人の端末のログイン状態を、こちらから直接切ることはできない**（認証は相手の端末の中にある）。

## 先に塞いだ穴

元のルールはこうだった。

```
allow update: if request.auth.uid in request.resource.data.members;
```

見ているのが**更新後**のメンバーなので、**スペースIDさえ知っていれば、招待コード無しで
自分を members に足して入れた**。外した相手はIDを端末に持っているので、そのまま戻れる。
＝ この穴がある限り「外す」機能は成立しない。

**直し方の選択肢を3つ比べた。**

| 案 | 内容 | 判断 |
|---|---|---|
| ban リスト | 外した uid を記録して弾く | 動くが、再招待したくなったとき詰む |
| スペースIDを変える | 記録22件・写真42枚(6.1MB)を新IDへ引っ越し。写真URLも書き換え | 外すたびに引っ越し。失敗すると思い出が壊れる |
| **参加をサーバ経由に**（採用） | コードの照合を Cloud Functions で行い、クライアントからの自己追加を禁じる | 外すのはコードの付け替えだけで済む。再招待も自然 |

## 仕組み

**参加** … `joinSpace` 関数（v2 onCall / us-central1 / admin 権限）が
`invites/{code}` を引いて `members` に追加する。二人までで、それ以上は `reason:'full'` を返す。
クライアントは members を書けない。

**外す** … `space.removeMember(spaceId, uid)` が1回の更新でまとめて行う。

1. `members` から相手を外す（Storage のルールも members を見ているので写真も同時に切れる）
2. `lastSeen.<uid>` を消す
3. `push.*` のうち相手の uid のものを消す（残すと記念日通知が届き続ける）
4. `inviteCode` を作り直す。新しい `invites/{code}` を**先に**作ってから古いものを消す
   （どちらも効かない瞬間を作らない）

**外された側** … 記録の購読が `permission-denied` になる。放っておくと「読み込み中」で
固まるので、`cloud.setOnDenied` で受けてログアウトし、事情を出して読み直す。
自分でログアウトしたときも同じエラーが出るため、`leaving` の印で区別する。

## ルール（firestore.rules）

- `spaces` の update は **いまの** メンバーだけ（`resource.data.members`）
- `invites` は読ませない（照合するのはサーバだけ）。作成・削除はそのスペースのメンバーだけ
- リポジトリに置いて `firebase deploy --only firestore:rules` で反映する

## 残っている弱点

- 招待コードの照合はサーバに移ったが、**スペースIDの推測**は依然として当てにしている部分がある
  （`spaces/{id}` の read は members 判定なので漏れない。create 済みIDへの参加は関数経由のみ）
- 相手の端末に**すでに表示されている画面**は消せない。次に開いた時点でアクセス不可になる
