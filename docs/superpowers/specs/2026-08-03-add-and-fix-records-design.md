# 設計：記録の「追加・修正をラクにする」3機能

- 日付: 2026-08-03
- 対象アプリ: デート記録（maprecord / GitHub Pages）
- 関連: [2026-08-01 地図記録の初期設計](2026-08-01-date-map-recorder-design.md), [2026-08-02 クラウド化(Firebase)](2026-08-02-cloud-storage-firebase-design.md)

## 目的

記録の「追加」と「位置の修正」にかかる手間・ストレスを減らす。現状の課題:

- 追加は **地図タップ or 現在地** のみ。店名から場所を探す手段がなく、「その店が地図上のどこか」を自分で探す必要がある。
- 作成時の座標が固定で、**ズレたピンをあとから直せない**。
- 記録した場所へ「次に行く」ときの導線（経路・営業情報）がない。

## スコープ

3つの独立機能。すべて **地図ビュー内で完結**し、**既存データ構造（`lat/lng/name/genre/...`）だけで実現**する。**Firestoreのスキーマ変更・データ移行は不要**。

- **A. 場所を検索して追加**（店名/地名 → ピン → 追加フォーム）
- **C. Googleマップで開く**（記録詳細から経路/営業情報へ）
- **D. 位置を修正**（編集画面からピンをドラッグ）

（元アイデアの B=写真EXIF自動入力 / E=行きたい場所リスト は今回のスコープ外。）

## 非スコープ（YAGNI）

- 有料ジオコーディング（Google Places 等）への対応。今回は無料の Nominatim のみ。
- 検索候補のお気に入り保存・履歴。
- 「行きたい場所」など新しいデータ種別の追加。
- 位置修正時の座標入力（数値手打ち）。ドラッグのみ。

## A. 場所を検索して追加

### UX フロー

1. 地図ビューに **「場所を検索」ボタン**（虫めがね＋ピン系アイコン）を新設。「現在地」ボタンの近くに配置。
2. タップ → 下シート（`#panel-content`）に **場所検索UI** を表示：入力欄＋検索ボタン。**Enter または検索ボタンで実行**（キーストロークごとの逐次検索はしない＝Nominatim のレートに優しく、挙動も明快）。
3. Nominatim を呼び、**候補を最大5件** リスト表示（表示名＋住所）。
4. 候補をタップ → その座標へ `flyTo` し、仮マーカーを置き、**既存の追加フォーム `showAddForm(lat, lng, { name })`** を場所名入りで開く（日付=今日、ジャンル=既定、メモ/写真/タグ=空）。
5. 以降は通常の追加保存フローに合流（クラウド保存→購読で自動反映）。

### ジオコーディング（`js/geocode.js` 新規）

- エンドポイント: `https://nominatim.openstreetmap.org/search`
- パラメータ: `format=jsonv2`, `q=<入力>`, `limit=5`, `accept-language=ja`, `addressdetails=1`, および **現在の地図表示範囲でバイアス**（`viewbox=<west,north,east,south>` + `bounded=0`＝範囲外も出すが近場を優先）。
- レスポンスから使う値: `lat`, `lon`, `display_name`（住所）, `name`（無ければ `display_name` 先頭要素）。
- 返り値の形: `[{ name, address, lat, lng }]`（最大5件）。
- **差し替え可能な設計**: `geocode.search(query, { viewbox })` という単一関数だけを公開し、records.js からはプロバイダ非依存で呼ぶ。将来プロバイダを変えても records.js は無変更。

### エラー/端の扱い

- 0件: シート内に「見つかりませんでした」を表示（アラートにしない）。
- 通信失敗/例外: `alert('場所の検索に失敗しました')`。検索UIは開いたまま再入力可能。
- 入力が空: 実行しない。
- 連打対策: 実行中は検索ボタンを一時無効化（多重リクエスト防止）。逐次検索はしないため、Nominatim のレート（毎秒1）に自然に収まる。

### Nominatim 利用ポリシー遵守

- リクエストは1件ずつ・ユーザー操作起点のみ（自動ポーリングしない）。
- ブラウザからの通常リクエスト（Referer 付与）で利用。大量利用しない。
- 二人利用の想定なのでポリシー範囲内。UI に OSM 由来の帰属表記が地図側で既に出ている（`&copy; OpenStreetMap contributors`）。

## C. Googleマップで開く

### UX

- 記録の**詳細パネル `showDetail`** に「Googleマップで開く」ボタンを追加（既存の「編集/削除」等の並び付近）。
- タップ → 新規タブで対象地点の Google マップページを開く。そこから経路案内・営業時間・電話へ辿れる。

### 実装

- リンク: `https://www.google.com/maps/search/?api=1&query=<lat>,<lng>`（座標指定で正確な地点を開く）。
- `window.open(url, '_blank', 'noopener')` もしくは `<a target="_blank" rel="noopener">`。
- 追加の権限・API キー不要。

## D. 位置を修正

### UX フロー

1. 記録の**編集フォーム `showEditForm`** に「位置を修正」ボタンを追加。
2. タップ → 地図が対象座標へ寄り、**ドラッグ可能なマーカー**を表示。ヒント「ピンをドラッグして正しい位置へ」を出す。下シートは地図が見える高さ（peek/half）へ。
3. ユーザーがマーカーをドラッグ → 新座標を保持。
4. フォームの「更新」保存時、**位置修正を行っていればその座標で `lat/lng` を上書き**、していなければ元の座標のまま。
5. 保存後は通常どおり詳細表示へ戻る（購読で地図も自動再描画）。

### 実装（`js/map.js` にヘルパー追加）

- `startPickLocation(lat, lng)`: 対象地点へ寄せ、ドラッグ可能マーカーを1つ表示（既存の一覧ピンとは別レイヤ/別マーカー）。
- `getPickedLatLng()`: 現在のドラッグ位置 `{ lat, lng }` を返す（未開始なら null）。
- `stopPickLocation()`: ドラッグ用マーカーを消す。
- records.js 側：`showEditForm` で「位置を修正」押下時に `startPickLocation`、キャンセル/更新完了/画面遷移時に `stopPickLocation`。更新時は `getPickedLatLng()` があればそれを採用。

### 端の扱い

- 位置修正を開始したが動かさなかった場合＝元座標のまま（`getPickedLatLng` は初期座標を返すが、実質同値）。
- 編集をキャンセル/戻る場合は `stopPickLocation` でマーカーを片付ける。

## テスト観点（手動・実機/本番）

- A: 店名で検索 → 候補表示 → 選択 → その地点にフォームが開き、保存で記録が出る。0件・通信失敗の表示。
- C: 詳細の「Googleマップで開く」で正しい地点が開く。
- D: 編集 →「位置を修正」→ ドラッグ → 更新でピンが移動して保存される。動かさなければ元のまま。キャンセルでマーカーが残らない。
- 既存機能（タップ追加・現在地追加・検索・カレンダー・二人同期）に影響がないこと。

## リスク / 留意

- **Nominatim レート/ポリシー**：ユーザー操作起点・デバウンス・少件数で範囲内に収める。将来重くなれば `geocode.js` 差し替えで対応。
- **座標上書き（D）**：`coordKey`（訪問まとめ）は座標で同一判定するため、位置修正で「同じ場所の複数訪問」グルーピングが変わり得る点は仕様として許容（正しい位置に直す行為なので妥当）。
